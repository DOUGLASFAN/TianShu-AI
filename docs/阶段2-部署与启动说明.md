## 2. 已准备好的本机直接启动

项目根目录 PowerShell：

```powershell
./scripts/start.ps1
```

脚本检查本地依赖、启动已有 PostgreSQL/Redis、执行迁移与幂等初始化、在隐藏窗口启动 API 和前端，再验证健康状态；不会自动打开浏览器，不会重置已有账号或删除数据。

打开 [星枢](http://127.0.0.1:5174/)。账号口令位于本机 `.local/config/demo-accounts.json`，包含 admin 和 student；口令随机生成，不写入源码、文档、截图或前端产物。

停止：

```powershell
./scripts/stop.ps1
```

仅停止应用进程、保留数据库运行可加 `-KeepServices`。停止脚本核对记录的 PID 与启动时间，避免 PID 复用时误停其他程序；服务数据始终保留。不要运行中手动移动 PostgreSQL 或 Redis 数据文件。

若本机策略禁止执行 PowerShell 脚本，不修改系统执行策略，可按下文 Python/Node 命令分别运行。

## 3. 新检出环境首次准备

需要可用 Node 24、Python 3.12、网络和 D 盘空间。在项目根目录执行：

```powershell
py -3.12 -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install --cache-dir .local/cache/pip -r backend/requirements.lock.txt
backend/.venv/Scripts/python.exe scripts/prepare_local_services.py
backend/.venv/Scripts/python.exe scripts/local_services.py start
backend/.venv/Scripts/python.exe -m backend.app.bootstrap
npm.cmd ci --prefix frontend --cache D:/AIcode/BeiDouApp/.local/cache/npm
npm.cmd --prefix frontend run prepare-assets
./scripts/start.ps1
```

下载脚本限定 PostgreSQL EDB ZIP 与 redis-windows 发布文件，并记录哈希；Redis 摘要与 GitHub 发布资产 digest 比对。PostgreSQL ZIP 的 SHA-256 是本机留存完整性值，没有独立官方摘要对照，不能表述为已完成发布方摘要验证。

本机 Redis 为社区 Windows 构建，**不宣称官方支持该原生版本**；容器配置使用官方 Redis 镜像。未启用 WSL、未注册 Windows 服务、未改变系统全局 Python 或包镜像配置。

如果没有阶段 1 全目录缓存，初始化使用仓库保留的三个真实样本，计数如实显示。当前本机已有完整已校验缓存，所以实际入库 16,899 条。全目录源刷新需网络并遵守上游限频。

## 4. 分别运行服务

终端一：

```powershell
backend/.venv/Scripts/python.exe scripts/local_services.py start
backend/.venv/Scripts/python.exe -m backend.app.bootstrap
backend/.venv/Scripts/python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8001
```

终端二：

```powershell
npm.cmd --prefix frontend run dev
```

独立采集进程（使用已有验证快照，不请求上游）：

```powershell
backend/.venv/Scripts/python.exe -m backend.worker --snapshot
```

省略 `--snapshot` 才执行在线/有效缓存采集。首次业务初始化标记 snapshot_seed，不把导入旧快照说成刚刚取得实时数据。

## 5. 验证与故障排查

- `/api/health/live` 仅验证 API 存活；`/api/health/ready` 实际连接数据库与 Redis。
- 端口占用时脚本不结束未知进程；先核对来源，或调整明确的项目端口与代理配置。
- 登录失败检查用户状态、来源限制、数据库与 Cookie；不要把口令粘进错误日志或聊天。
- 根目录 `.env` 的密钥和口令来自项目初始化；保留已有文件，不用 `.env.example` 覆盖有效配置。
- 第三方来源不可用时读本地库与来源缓存；后台采集日志保留错误代码，不能清空有效目录。
- API 的未知错误响应不暴露堆栈。`requestId` 可用于关联一次请求，但本阶段未交付完整运维日志平台。

测试：

```powershell
backend/.venv/Scripts/python.exe scripts/verify_phase2_backend.py
backend/.venv/Scripts/python.exe scripts/verify_phase2_persistence.py
```

必须**串行**执行，持久化脚本会重启本项目 PostgreSQL/Redis，不能与依赖它们的集成或浏览器测试并发。集成测试新建独立数据库，Redis 使用 DB 15，不清空正式库。测试库保留作证据，后续如需清理只处理明确命名的测试库。

前后端启动后，在 frontend 目录执行 `node verify-browser.mjs`。测试使用独立浏览器配置、不会登录用户已有浏览器或导出浏览器资料。

## 6. Compose 备选配置（尚未运行验证）

已有 Docker Desktop/Engine 与 Compose 后，在根目录：

```powershell
docker compose config --quiet
docker compose up --build -d
```

需要根目录私有 `.env` 中已生成的 STAR_DB_PASSWORD、STAR_DB_ADMIN_PASSWORD、STAR_REDIS_PASSWORD、STAR_JWT_SECRET。Compose 内部通过服务名连接，Nginx 入口为 127.0.0.1:8080，PG/Redis 对宿主机另用 15432/16379，避免与原生实例冲突。

Compose 包含健康检查与依赖启动顺序，使用官方 PostgreSQL/Redis Linux 镜像，应用角色为非超级用户。容器数据独立存储，不能复用原生 Windows 数据目录。**当前 Docker 缺失，因此这里只交付配置，容器实际部署仍须后续环境可用时验收**。
