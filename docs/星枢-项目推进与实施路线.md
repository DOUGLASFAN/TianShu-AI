## 1. 开发方式与执行原则

采用“演化式原型 + 迭代增量开发”：先验证最关键的数据、算法和三维体验，再把可运行原型逐步完善为完整系统。每轮都完成需求细化、设计、实现、实际体验、验证和记录，不等全部功能写完才联调。

需求文档回答“做什么、做到什么程度”，本文回答“先做什么、依赖什么、每一步怎样算完成”。功能边界以需求文档为准；本文进一步拆解实施过程。

执行原则：

1. 每轮交付一条可实际操作的业务链路，前端、后端与数据库一起推进。
2. 从第一轮可运行原型开始保持 A 风格的视觉质量，后续逐步精修动画；不把全部外观工作拖到最后。
3. 先验证数据源和算法，再扩展依赖它们的页面；临时样本必须标明来源和时效。
4. 鉴权、数据来源、错误状态、缓存与持久化随功能一起建设，不能只在收尾时补。
5. 首轮建立开发与部署骨架，末轮验证干净环境下的启动；不把部署问题留到答辩前一天。
6. 普通实现决策按已确认范围自主推进；重要体验节点给用户可操作结果与截图，反馈纳入下一轮。
7. 每轮只运行与改动相关的验证，发现新风险再扩大检查，保留有用证据。

## 3. 总体顺序与依赖

主线如下：

**需求与视觉基线 → 数据/算法/三维可行性验证 → 工程骨架与认证 → 卫星探索高保真原型 → 实时与目录规模化 → 观测站与单星预测 → 分组预测与回放 → 观测计划与提醒 → 天气/大屏/管理完善 → 综合验收与性能精修 → 部署与答辩。**

依赖关系：

- 地球点位、轨道和跟踪依赖可靠的轨道解析、坐标与采样协议。
- 过境预测依赖轨道计算、星历文件和观测站；计划与提醒依赖已经验证的预测事件。
- 空间天气依赖独立数据接入；聚合大屏依赖目录、元数据和统计口径。
- 管理后台的采集任务状态与日志在采集服务建立时就产生，后续再完善页面。
- 性能和动画随各轮优化，最后一轮做跨模块一致性与连续运行验证。

## 4. 阶段 0：冻结首版范围，明确视觉语言

目标：让功能与界面有共同基线，避免开发过程中反复更换产品方向。

任务顺序：

1. 对照课程 A-1～A-10 形成验收清单，标记必做、可选和不做内容。
2. 将 A 风格明确为主方向：真实地球、深蓝黑背景、轻玻璃面板、青蓝交互、琥珀色强调。
3. 制定颜色、字体层级、间距、圆角、面板边界、按钮、图标、图表与状态规范。
4. 绘制探索首页关键状态：未选中、选中、跟踪、加载、无结果、数据过期、连接断开。
5. 细化六个页面的入口和核心操作流程，先规定探索与观测的布局。
6. 列出动画分工：Cesium 管地球与相机，Motion 管界面，GSAP 只管确有需要的编排。

交付物：视觉与交互规范、核心页面状态清单、课程验收任务表。

完成条件：能根据规范开始编写真实页面；效果图中仅用于示例的日期、参数和卫星图标不会直接当作真实数据使用。

## 5. 阶段 1：验证最容易影响全局的技术风险

目标：用小规模验证确认数据、计算与地球效果可落地，先处理会迫使架构调整的问题。

任务顺序：

1. 检查本机 Node、Python、Docker、浏览器等运行条件，记录实际可用版本，不读取或输出密钥。
2. 从后端验证 CelesTrak 轨道数据、元数据、ISS 和空间天气来源的连通性与字段，记录响应和限制。
3. 准备有来源、原始时间和文件校验信息的样本，验证 TLE 与结构化 GP 输入。
4. 使用 ISS、代表性的导航卫星及 GEO 对象验证传播、经纬度、高度、速度、单位和时区。
5. 为一个固定观测站验证过境起止、最高点、太阳高度和卫星受光；准备固定输入的参考结果。
6. 验证 Cesium 加载本地基础地球资源、采样轨迹、标记和相机定位，不依赖在线瓦片才能启动。
7. 做小规模动态点位试验，识别点位更新与 React 重渲染的边界。

交付物：数据接入与可行性记录、算法验证样例、资源与许可清单、可复用的三维和计算验证代码。

完成条件：至少一颗真实公开卫星可以从后端数据解析到地球展示；固定时间结果可复核；无网络时基础地球可以打开。暂不可用的数据源必须有明确替代或回退路径。

## 6. 阶段 2：建立工程骨架、数据基础与认证

目标：让后续原型建立在可维护、可部署的工程上。

任务顺序：

1. 建立前端、后端、后台任务、基础设施、文档、资源目录，以及依赖锁定与环境样例。
2. 组织后端 API、业务服务、数据访问、数据源适配器、轨道计算和后台任务模块；保持单体应用的清晰分层，不扩展为不必要的微服务。
3. 建立 PostgreSQL、Redis、初版 Compose 与数据库迁移，初始化用户、卫星、分组、根数、关注及采集记录。
4. 明确接口字段、时间、坐标单位、分页响应、错误码、requestId 和数据状态结构。
5. 完成注册、登录、Token 验证、角色校验、退出、演示账号和普通用户访问隔离。
6. 完成基础采集入库、原始记录留存、有效版本更新、缓存和失败日志。
7. 建立前端路由、布局、登录状态、统一 API 调用和基础错误提示。

交付物：可启动工程、数据库迁移、登录页、基础 API、初版启动说明。

完成条件：新建环境可初始化并登录；未登录业务请求返回 401；数据写入后重启可回查；前端不携带第三方密钥且不直连第三方业务接口。

## 7. 阶段 3：完成 A 风格卫星探索高保真原型

目标：首先交付用户可以体验的核心样板，确定后续全部页面的质量标准。

任务顺序：

1. 搭建真实地球、光照/大气效果、目录栏、详情栏、时间控制和状态区域。
2. 接入后端分页目录、搜索、分组和详情；从少量代表对象开始，再扩充数据量。
3. 展示后端计算的位置采样与轨迹，前端插值实现连续运动，检查坐标系和时间一致。
4. 实现点击列表/点位选择、定位、跟踪、退出、恢复全球视角。
5. 完成关注写入、查询与去重；保存后重启仍能显示。
6. 打磨入场、面板开合、目标切换、相机飞行和轨道显示；处理连续点击与动画取消。
7. 完成加载、无结果、字段未知、采样失效和陈旧数据状态。
8. 在浏览器实际检查三种桌面分辨率，保留截图与交互录屏，根据用户反馈调整样板。

核心演示：**登录 → 搜索 ISS → 查看详情 → 定位 → 跟踪 → 关注 → 退出跟踪 → 恢复全球视角。**

交付物：可运行探索首页、基础设计组件、第一段实际演示录像。

完成条件：操作和数据真实连接；画面接近 A 的设计语言；相机不穿地、不明显跳变；反复切换对象无残留轨道或持续增长的订阅。

## 8. 阶段 4：接入实时链路，扩展目录与数据可信度

目标：让少量卫星的漂亮样板演化为可持续更新的全球目录平台。

任务顺序：

1. 建立独立采集与计算任务进程，落实轨道每 2 小时、ISS 每 10 秒、统计每 5 分钟缓存策略；遵守上游更严格限制。
2. 完成一次性 WS 连接票据、心跳、可视集合订阅、初始快照与增量消息。
3. 实现断线退避重连、恢复后补快照、消息乱序处理、授权失效处理。
4. 接入元数据，补齐轨道/国家/用途筛选，展示未知项与覆盖范围。
5. 实现全目录总览、分组切换、标签控制、批量采样、关注轨道上限及资源清理。
6. 完成根数历元、采集时间、连接状态、数据质量及来源标识。
7. 验证外部超时、缓存命中、数据库回退、演示快照、Redis 暂不可用时的行为。

交付物：实时探索版本、自动任务和日志、可信度状态组件、首轮性能记录。

完成条件：断开 WS 后可自动恢复；上游失败不清空目录；演示快照不会标为实时；默认集合与全目录总览的性能分别实测。基础全局目录不足时显式显示实际覆盖量。

## 9. 阶段 5：建立观测站与单星过境预测

目标：完成项目最重要的计算型功能，并建立可复核的结果标准。

任务顺序：

1. 完成观测站表、接口、用户归属和坐标校验；支持点选、输入、保存、修改和默认站。
2. 固化几何过境规则、最低仰角、UTC 存储与 UTC+8 展示；查询未来 24 小时、3 天、7 天。
3. 完成后台预测任务的基础状态：排队、执行、成功、失败、取消和过期。
4. 实现单星进入/最高点/离开、仰角、方位角和持续时间计算。
5. 实现太阳高度与受光条件，细化并输出潜在目视观测子窗口。
6. 保存根数版本、观测站快照、阈值与算法版本；展示数据过期和计算依据。
7. 接入观测规划表单、结果列表、详情与仰角曲线。

交付物：观测站管理、单星预测流程、固定输入验证集、算法口径说明。

完成条件：保存站点后可重用；固定输入结果稳定；时区、无过境、跨边界、持续可见、多受光窗口与传播失败均有正确处理。数值分辨率不被表述为实际观测精度。

## 10. 阶段 6：完成分组预测、三维回放与观测计划

目标：把预测结果转化为可探索、可保存的业务成果。

任务顺序：

1. 扩展分组预测、批次范围、任务上限、进度、取消和分页，避免静默截断或阻塞 API。
2. 对固定观测站与条件进行合理缓存，记录对象范围与根数版本，更新后避免误用旧缓存。
3. 实现结果筛选、排序和潜在目视窗口标记。
4. 建立统一模拟时钟，同步地球位置、地面轨迹、时间轴与曲线游标。
5. 实现播放、暂停、拖动、速度切换、回到当前时刻；模拟时钟不影响提醒调度。
6. 保存观测计划，保留计算快照；支持查看、取消和重新计算。
7. 完善我的空间中的关注、观测站和计划列表，保证跨页面跳转保留必要上下文。

交付物：完整观测规划页面、过境回放、观测计划和我的空间。

完成条件：**选站 → 批量预测 → 筛选 → 回放 → 保存 → 重启后查看**可以完整演示；取消任务不继续向用户发送成功通知，回放中各组件使用同一时刻。

## 11. 阶段 7：完成提醒与空间天气安全主题

目标：让平台从“看轨道”进一步形成观测行动与环境风险提示。

任务顺序：

1. 根据计划建立真实系统时间驱动的提醒调度，支持 5/10/30 分钟阈值。
2. 完成提醒去重、已读状态、计划取消撤销、版本重算、重启后恢复与错过状态。
3. 经 WS 推送站内提醒，完成通知中心；应用关闭不承诺送达。
4. 接入天气指标与事件采集、原始数据留存、来源时间和过期规则。
5. 完成空间环境概览、趋势、事件列表、详情与筛选。
6. 区分观测/预测/官方预警，用有来源的说明解释潜在影响，数据未知时不能显示正常。

交付物：站内提醒、空间环境页面、数据时效与风险解释。

完成条件：单一提醒不会重复；取消和重算后的行为正确；天气失败有降级提示；不把一般性空间天气影响解释为本地已发生故障。

## 12. 阶段 8：完成统计大屏与管理中心

目标：补齐课程集中展示与运维解释能力。

任务顺序：

1. 固化互斥轨道分类、元数据覆盖率、发射卫星数量、分组去重和未知项统计口径。
2. 完成后端聚合接口和缓存，对结果做数量一致性检查。
3. 完成大屏指标、轨道分布、发射趋势、国家/用途占比、地球和滚动榜单。
4. 实现 1920×1080 基准等比缩放、全屏与退出、留边及异常状态提示。
5. 管理页面展示此前已运行的采集日志、数据源状态、任务队列和手动刷新。
6. 完成用户启停、权限边界、任务去重与限流、明确标识的故障演示控制。

交付物：态势大屏、管理中心、统计口径与课程验收映射更新。

完成条件：图表全部来自自有接口；分组不重复累计；元数据缺失不编造；大屏无滚动条；普通用户不能调用管理接口；失败任务在日志中如实保留。

## 13. 阶段 9：综合验收、动画精修与性能优化

目标：达到稳定、统一、可解释的最终质量，关闭跨模块问题。

任务顺序：

1. 按需求文档逐项验收，建立缺陷表，先处理阻断、错误数据、权限和持久化问题。
2. 跑完整核心流程及异常流程，检查多用户资源隔离、重复提交和数据一致性。
3. 统一各页面的排版、状态、图表、焦点、弹窗与动画节奏，完善减少动态效果选项。
4. 测量首屏、接口 P95、单星/分组预测、2000 点默认场景和 10000 点总览；记录真实数据量与测试环境。
5. 根据测量定位采样、渲染、标签、网络或数据库瓶颈，优化后只复测相关项。
6. 连续运行 30 分钟，反复切页、跟踪、回放、断线与恢复，检查资源释放与稳定性。
7. 检查三种分辨率、大屏缩放、浏览器全屏失败和冷启动状态。

交付物：功能验收记录、实际性能数据、缺陷关闭记录、最终页面截图与录屏。

完成条件：核心流程无未解决阻断问题；课程要求全部有证据；性能目标逐项给出实测结果。未达到的指标必须说明场景与处理结果，不能把目标写成实测成绩。

## 14. 阶段 10：交付、启动演练与答辩准备

目标：让项目在演示当天可以按文档启动、按脚本讲清、遇到断网仍可展示。

任务顺序：

1. 整理 Compose、迁移、初始化、配置样例、资源准备、健康检查和启动顺序。
2. 区分首次安装准备与日常一键启动；明确首次准备需要的网络和依赖。
3. 在独立环境或新配置下验证安装与初始化，不删除现有数据库来冒充干净启动；先备份演示数据。
4. 固化演示账号、关注列表、观测站、近期计划、带来源快照及本地地球资源。
5. 编写启动/停止/备份恢复/常见故障说明、API 文档、架构和算法说明、资源来源记录。
6. 制作 PPT：个人介绍与分工、需求、架构、核心功能、困难与解决、特色、实训收获。
7. 准备正常网络与断网两套演示路线，录制实际操作视频作为展示备份。
8. 保留可回退的交付版本，最后阶段只修复影响交付的问题；额外扩展放到后续迭代。

交付物：完整源码和运行环境说明、测试与演示材料、PPT、交付版本记录。

完成条件：按文档可启动；数据库可回查；演示脚本完整走通；所有材料与实际功能一致，不虚构成员、功能或效果。

## 17. 每轮工作与记录方式

每轮开始确定一条具体目标，例如“保存观测站后重新登录还能选择它”。实现时同步更新 API 和迁移；结束时给出运行方式、完成内容、验证结果、截图/录屏和剩余问题。

任务状态统一使用：未开始、进行中、待验证、已完成、受阻。只有实际实现并通过对应完成条件，才能标记已完成；只有计划、截图或接口定义不算功能完成。

验收与进度统一在[阶段验收清单](./阶段验收清单.md)维护；必要的详细测试与数据报告另行链接。其他配套文档：

- `docs/阶段验收清单.md`：阶段状态、任务勾选、下一步、验证证据和阻碍，已创建。
- `docs/视觉与交互规范.md`：A 风格组件与动画规范。
- `docs/数据接入与算法验证.md`：来源、样本、计算口径与参考结果。
- `docs/验收与测试记录.md`：课程映射、实际性能和缺陷。
- `README.md`：启动入口；部署及答辩细节按需要拆分。

以上为后续应建立的文档，不表示目前均已存在。日常功能可记录在同一进度表中，不为每个小修改增加独立文档。
